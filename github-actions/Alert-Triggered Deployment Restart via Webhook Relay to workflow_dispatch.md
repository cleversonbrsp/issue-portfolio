# 🔁 Automação: Restart de Deployment Disparado por Alerta de Monitoramento via Webhook (Relay para workflow_dispatch)

## 🇧🇷 Português (BR)

**issue:**
Uma aplicação em produção apresentava lentidão intermitente, mitigada manualmente com o restart do deployment. Era necessário automatizar esse restart a partir do alerta da plataforma de monitoramento (latência p90 de um endpoint acima do limite), acionando um workflow do GitHub Actions. O webhook da plataforma, porém, envia um corpo JSON fixo (formato Alertmanager), sem template e sem o campo `ref`, que a API de `workflow_dispatch` do GitHub exige. Chamar a API diretamente resultaria em erro 422. Além disso, no primeiro teste manual do restart, os pods novos reiniciaram por 502 ao buscar configuração (serviço de configuração com réplica única e instável) e o deployment não tinha probes, então o `rollout status` reportava sucesso mesmo com pods caindo depois.

**causa raiz:**
Incompatibilidade de contrato entre o webhook da plataforma de monitoramento (corpo fixo, sem `ref`) e a API de `workflow_dispatch` (`ref` obrigatório). Somado a isso, a ausência de probes de readiness/liveness fazia o rollout ser considerado concluído assim que os contêineres subiam, e a dependência de um serviço de configuração instável (réplica única) podia derrubar os pods novos logo após o restart.

**solução:**
Foi criado um relay mínimo (nginx em Docker, na mesma rede Docker da plataforma de monitoramento, sem porta publicada, versão fixa, limite de memória e healthcheck) que valida a autenticação (basic auth), aceita só POST e chama o endpoint de dispatch do workflow com o `ref` fixo. O token do GitHub é fine-grained, restrito a um único repositório (Actions: Read and write, Metadata: Read-only), de uma conta dedicada, com validade e armazenado em arquivo de permissão restrita fora do Git. Ao trocar o token, um 403 "Resource not accessible by personal access token" mostrou que o token fine-grained nunca excede o papel da conta no repositório (a conta tinha só leitura); concedido o papel Write, a chamada passou a retornar 204. O workflow de restart ganhou proteções: cooldown por anotação do deployment, pré-checagem do serviço de configuração (observa uma janela e bloqueia se instável), `rollout status` com timeout, verificação de estabilização (pods Ready e `restartCount` 0 por 5 minutos) e notificação no Teams em todos os casos. A cadeia foi validada primeiro com um workflow de teste que apenas imprime uma linha (sem risco em produção), depois com disparos manuais e um alerta simulado. O canal do webhook foi associado à regra existente só ao final, com desligamento simples (remover o canal da regra ou parar o contêiner do relay). Recomendações: probes no deployment, mais de uma réplica no serviço de configuração e revisão periódica do teto de restarts.

## 🇺🇸 English

**issue:**
A production application showed intermittent slowness that was mitigated manually by restarting its deployment. The restart needed to be automated from the monitoring platform alert (endpoint p90 latency above a threshold), triggering a GitHub Actions workflow. However, the platform's webhook sends a fixed JSON body (Alertmanager format), with no body template and no `ref` field, which the GitHub `workflow_dispatch` API requires. Calling the API directly would return a 422 error. In addition, during the first manual restart test, the new pods restarted because of 502 errors while fetching configuration (a single-replica, unstable configuration service), and the deployment had no probes, so `rollout status` reported success even though pods failed afterwards.

**root cause:**
A contract mismatch between the monitoring platform's webhook (fixed body, no `ref`) and the `workflow_dispatch` API (`ref` required). On top of that, the lack of readiness/liveness probes made the rollout count as complete as soon as the containers started, and the dependency on an unstable single-replica configuration service could take down the new pods right after the restart.

**solution:**
A minimal relay (nginx in Docker, on the monitoring platform's Docker network, with no published port, pinned version, memory limit and healthcheck) was created. It validates authentication (basic auth), accepts only POST and calls the workflow dispatch endpoint with a fixed `ref`. The GitHub token is fine-grained, limited to a single repository (Actions: Read and write, Metadata: Read-only), owned by a dedicated account, with an expiry date, and stored in a restricted-permission file outside Git. When replacing the token, a 403 "Resource not accessible by personal access token" showed that a fine-grained token never exceeds the account's role on the repository (the account only had read access); once the Write role was granted, the call returned 204. The restart workflow gained safeguards: cooldown through a deployment annotation, a pre-check of the configuration service (observes a window and blocks if unstable), `rollout status` with a timeout, a stabilization check (pods Ready with `restartCount` 0 for 5 minutes) and a Teams notification in every case. The chain was validated first with a test workflow that only prints a line (no production risk), then with manual runs and a simulated alert. The webhook channel was attached to the existing rule only at the end, with a simple off switch (remove the channel from the rule or stop the relay container). Recommendations: add probes to the deployment, run more than one replica of the configuration service and periodically review the cap on restarts.
